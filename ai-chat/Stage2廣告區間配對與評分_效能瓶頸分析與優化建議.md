# Stage 2 廣告區間配對與評分：效能瓶頸分析與優化建議

## 1. 背景與現況說明

在目前影片去廣告（`remove_video_ad`）的處理管線中，流程分為三個階段：
- **Stage 1（全片快速掃描）**：每秒抽樣 3 格，透過色彩直方圖與邊緣變化，粗略篩選全片的劇烈切換點集合（Cut Points $T_{cuts}$）。
- **Stage 2（廣告區間配對與評分）**：將切點組合配對為候選廣告區間，檢驗區間時長、正片前後呼應度、廣告內部色彩穩定度（圖卡特徵）與反差度，最後以 IoU 去重。
- **Stage 3（邊界逐格精確化）**：針對通過的高信心區間局部搜尋最佳切割點。

**問題反饋**：
目前 **Stage 2 佔據了相當顯著的執行時間**，且在追求高準確率（不漏抓、不誤切正片）的前提下，需要找出顯著提速的解法。

---

## 2. 核心效能瓶頸排查（代碼層級診斷）

經檢視 `stage2_pair.py` 與 `frame_extractor.py` 的實作，發現 Stage 2 之所以耗時，並非數學模型或演算法複雜度過高，而是**「I/O 隨機解碼開銷過大」與「缺乏快取與早停」**所致：

### 瓶頸 1：OpenCV `CAP_PROP_POS_FRAMES` 頻繁隨機尋軌解碼（最主要耗時點）
* **機制**：多數現代影片採用 H.264 / H.265 的 GOP（Group of Pictures）壓縮結構，關鍵影格（I-Frame）之間可能相隔數十到上百格。
* **現狀**：當使用 `extractor.get_frame(f_idx)` 時，OpenCV 會強制透過 `set(cv2.CAP_PROP_POS_FRAMES, f_idx)` 跳轉。若目標格不是關鍵影格，底層解碼器必須先回溯至前一個 I-Frame，再一路逐格向前解碼至目標格。
* **代價**：在雙重配對迴圈中，只要時長介於 18~32 秒，每個候選區間就會呼叫 `get_frame` **高達 6 次**（前後正片各 1 格 + 內部均勻取樣 4 格）。若有 80 組候選，等於要在時間軸上前後跳躍進行近 **500 次的硬解碼**，造成硬碟與解碼器的嚴重負荷。

### 瓶頸 2：`get_frame` 無快取，重複解碼相同影格與重複計算特徵
* **現狀**：雖然 `frame_extractor.py` 定義了 `_frame_cache`，但僅綁定在 FFmpeg 的 `get_exact_frame`；Stage 2 呼叫的 `extractor.get_frame` **完全沒有任何快取**。
* **代價**：
  - 同一個切點 $cp_{in}$ 若與多個 $cp_{out}$ 配對（例如 20s、25s、30s 各有一處切點），其前 1 秒的影格 `f_before` 與 HSV/Canny 特徵（`compute_frame_features`）會被**重複解碼並重複計算多次**。
  - 同理，同一處 $cp_{out}$ 的 `f_after` 也被反覆重新讀取。

### 瓶頸 3：缺乏無成本的「先驗早停剪枝」（先解碼才篩選）
* **現狀**：只要區間長度符合 `18 <= dur <= 32` 秒，程式碼便無條件立刻把 6 張影格全部解碼取出。
* **代價**：
  - `score_dur`（時長分數）與 `score_cut`（切點強度）為純數學與 Stage 1 既有數值，**完全不需解碼即可計算**。
  - 對於時長極其邊緣、且切點強度極差的組合，其最終綜合得分必然偏低，但程式依然先花費時間解碼 6 張圖，造成大量無效運算。

### 瓶頸 4：內部穩定度檢驗未設置 Early-Exit
* **現狀**：內部取樣 4 個時間點（20%、40%、60%、80%），程式碼無條件全數解碼並計算特徵後，才在最後判定是否超過 `max_internal_variance`。
* **代價**：若前 2 個採樣點之間的相異度就已經遠超過 0.45（典型正片鏡頭快速切換），此區間已註定淘汰，但後續 2 個採樣點仍被浪費性地解碼。

## 3. 保證準確度前提下的三部曲優化方案

本優化方案完全不調動核心特徵評分邏輯（HSV 直方圖比對、Canny 邊緣、高斯時長分佈、正片呼應反差比對均保持不變），純粹透過**減少重複解碼、避免無效解碼**來達成顯著加速。

```
[候選切點配對 (i, j)]
       │
       ▼ (18s <= dur <= 32s)
┌─────────────────────────────────┐
│ 步驟 2：純數值先驗快篩 (零 I/O)    │  ---> [時長過差或切點極弱] 直接 continue
└─────────────────────────────────┘
       │ 通過 (約減少 30%~50% 組合)
       ▼
┌─────────────────────────────────┐
│ 步驟 1：前後正片特徵快取讀取      │  ---> 同一切點全片只解碼 1 次、特徵只算 1 次
└─────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────┐
│ 步驟 3：內部穩定度採樣與 Early-Exit│  ---> 邊讀邊驗證，若前段鏡頭差異過大立即中斷
└─────────────────────────────────┘
       │ 通過穩定度檢驗
       ▼
[計算加權總分與 IoU 去重]
```

---

### 步驟 1：建立本地「特徵與影格快取池」
在 `pair_and_score` 函式內部維護影格特徵快取字典，同一個影格索引全片只解碼一次、特徵只計算一次：

```python
# 局部快取：frame_index -> (hist_hsv, edge_density)
feat_cache: dict[int, tuple[np.ndarray, np.ndarray] | None] = {}

def get_cached_feature(f_idx: int) -> tuple[np.ndarray, np.ndarray] | None:
    if f_idx not in feat_cache:
        img = extractor.get_frame(f_idx, target_size=(160, 90))
        feat_cache[f_idx] = compute_frame_features(img) if img is not None else None
    return feat_cache[f_idx]
```

---

### 步驟 2：純數值先驗過濾（Cheap Math Pre-filter）
在呼叫任何畫面解碼前，利用已知的 `dur` 與 `diff_score` 進行初篩：

```python
score_dur = _duration_score(dur, cfg.target_duration, cfg.duration_sigma)
score_cut = 0.5 * (cp_in.diff_score + cp_out.diff_score)

# 當離目標時長（25s）過遠，且切點訊號微弱時，直接略過，省下所有影格解碼
if score_dur < 0.15 and score_cut < 0.45:
    continue
```

---

### 步驟 3：內部穩定度採樣「延遲加載與早停」
將一次性讀取改為逐格檢查，若前期變化率過大則立即放棄：

```python
internal_samples = [
    int(s_frame + (e_frame - s_frame) * r) for r in (0.2, 0.4, 0.6, 0.8)
]

internal_feats = []
aborted = False
for f_idx in internal_samples:
    feat = get_cached_feature(f_idx)
    if feat is not None:
        if internal_feats:
            step_diff = compare_frames(internal_feats[-1], feat)
            # 單步差異劇烈（明顯為一般劇情運鏡切換），立即放棄該候選
            if step_diff > cfg.max_internal_variance * 1.4:
                aborted = True
                break
        internal_feats.append(feat)

if aborted or len(internal_feats) < 2:
    continue
```

## 4. 預期效益與影響評估

| 指標項 | 優化前 | 優化後（預期） | 改善幅度 |
| :--- | :--- | :--- | :--- |
| **OpenCV Seek 解碼次數** | 300 ~ 600 次 | 60 ~ 120 次 | **降低 70% ~ 80%** |
| **重複特徵計算** | 普遍存在（同切點重複算） | 零重複（透過快取保證） | **消除 100% 重複計算** |
| **Stage 2 耗時** | 30 ~ 60 秒（依影片與切點數） | 5 ~ 10 秒 | **提速約 3~6 倍** |
| **廣告抓取準確度** | 基準線 | **完全不變（100% 保持）** | 評分公式與去重邏輯一致 |

## 6. 補強建議：落地前檢核、風險控制與進一步優化

上述「特徵快取 + 純數學預篩 + Early-Exit」是正確的第一步；但 Stage 2 除了要縮短時間，也必須維持高召回率（不漏抓廣告）。以下事項應一併納入設計與驗證。

### 6.1 先量測，再設定效能目標

第 4 節的「降低 70%～80%」與「3～6 倍提速」應視為待驗證假設，而非保證；實際結果會受編碼格式、GOP 長度、解析度、儲存裝置快取及切點密度影響。建議在 `pair_and_score` 加入可開關 profiling，記錄：

- 時間窗內的候選配對數、預篩後候選數、最後保留候選數。
- `get_frame` 呼叫數、唯一影格索引數、feature cache hit / miss 數。
- 解碼、特徵計算、評分、去重各自耗時。

應以同一批含真值的影片，比較優化前後的耗時、正確區間是否仍存在，以及正確候選的排名是否下降。

### 6.2 快取應以 feature 為主，並正確認知收益範圍

現有 `FrameExtractor._frame_cache` 僅由 `get_exact_frame()` 使用；Stage 2 使用的是 `get_frame()`，因此不會命中該快取。建議在 Stage 2 建立 `frame_index -> feature | None` 的區域快取，使同一影格只解碼與計算特徵一次。

內部均勻取樣影格在不同候選間未必重複，因此 feature cache 的主要收益是消除共用切點前後 context 影格的重複工作，不能單靠快取推估整體大幅加速。若將影格快取下沉至 `FrameExtractor.get_frame()` 供其他功能共用，key 應包含 `(frame_index, target_size)`，並採可設定上限的 LRU，以避免長片占用過多記憶體。

### 6.3 優先採用兩階段處理與批次解碼

比起逐候選隨機 seek，更有效的流程如下：

1. 先枚舉符合時長窗的候選，只計算 `duration` 與 `cut_strength` 等零 I/O 分數。
2. 依廉價分數做保守排序或淘汰，保留足以維持召回率的候選集合。
3. 彙整這些候選所需的影格索引，去重、依時間排序，將鄰近索引分群後連續解碼。
4. 對已載入的 feature 計算穩定度、前後 context 與反差度。

現有 `FrameExtractor.get_frame_range()` 可作為分群連續解碼的基礎。分群距離需依實測 GOP 與影片長度調整；間隔太大而硬讀中間所有影格也可能反而浪費時間。

### 6.4 預篩與 Early-Exit 必須可設定且保守

範例中的 `score_dur < 0.15 and score_cut < 0.45` 不應硬編碼，應改為 `PairConfig` 參數，並使用含真值資料校準。低切點強度的廣告仍可能因穩定度、前後正片呼應或反差度而成為高分候選；門檻過高會造成漏抓。

Early-Exit 也不宜僅因一對內部樣本差異偏高就直接淘汰。SRS 要求容許字幕更換、局部動畫及閃爍；單一步差異可能是正常廣告行為。較安全的策略是：只有在目前累積差異已使最終平均值不可能低於門檻時才停止，或先降分再交由總分排序。

### 6.5 修正樣本不足與解碼失敗的判定

目前若所有內部影格都無法解碼，`internal_diffs` 為空時會使用預設 `avg_internal_diff = 0.5`，候選仍可能依其他分數被保留。應設定最少成功內部樣本數（例如至少 3 個）；不足時要明確跳過、標示為不可評估，或以低可信度另行保留。不可將解碼失敗誤認為畫面穩定。

### 6.6 配對迴圈與規格一致性

- `pair_and_score` 依賴 `cut_points` 已依時間排序，且會掃過所有小於最短時長的 `j`。建議函式內排序／驗證，並以 `bisect` 找出每個起點可配對的最小與最大索引，降低高切點密度影片的迴圈成本。
- SRS Stage 2 定義時長窗為 **15～35 秒**，目前 `PairConfig` 預設為 **18～32 秒**。若為刻意收緊以提高精準度，應在 SRS 或設定說明中記錄；否則應調整預設值一致。
- 模組註解寫「取 5～7 格」、程式註解寫「取 5 個時間點」，但實作取 `0.2、0.4、0.6、0.8` 共 4 格。應統一文件與程式，並以召回率和耗時驗證樣本數取捨。

### 6.7 可取消性與回歸測試

Stage 2 應接受 `cancel_event` 並回報候選處理進度，避免長片或高切點密度時 GUI 看似失去回應。另建議新增測試：

- 同一切點配對多個終點時，確認 feature 只計算一次。
- 解碼失敗或內部樣本不足時，不會產生「假穩定」高分候選。
- 含字幕、局部動畫、短暫閃爍的廣告，Early-Exit 不會錯誤淘汰。
- 大量正片切點影片的候選枚舉不會因無效配對明顯惡化。
- 優化前後皆能找回真值區間，且正確候選排序沒有明顯下降。

### 6.8 建議實作順序

1. 加入 profiling 與真值回歸測試，建立基準。
2. 實作 Stage 2 feature cache，以及解碼失敗／樣本不足的正確處理。
3. 將 duration / cut 預篩參數化，使用測試資料校準保守門檻。
4. 導入候選影格彙整、排序與分群的批次連續解碼。
5. 最後才啟用經驗證的 Early-Exit，持續比較召回率與排名。
