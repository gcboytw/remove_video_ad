# 方案 1：邊界精確抽圖與「所見即所得」修改計畫

## 1. 問題核心診斷：為什麼會多留 1 秒廣告？

在最近的測試中，指定刪除廣告區間 `7199 - 7818`，轉檔後卻在銜接點（新影片 `7193 - 7216`）殘留了約 1 秒（24 格）的廣告畫面。

### 根本原因分析（⚠️ 以下為推論，須先經「步驟 0」驗證）
> 另一個同樣可能的原因 **B**：exporter 的 `trim` 以 frame 編號計算，在 VFR 或 `start_time ≠ 0` 時與 PTS 對不上。
> 若診斷結果顯示 OpenCV 與 FFmpeg 一致，則問題在 exporter，本計畫方向要反過來改 exporter。

1. **OpenCV 的 B-frame 跳格誤差（Seek Discrepancy）**：
   - 目前 GUI 的邊界檢視器（`BoundaryView`）是透過 `FrameExtractor` 呼叫 OpenCV 的 `cv2.VideoCapture.set(cv2.CAP_PROP_POS_FRAMES, frame_idx)`。
   - 對於現代 MP4（H.264 / H.265），影格具有複雜的依賴結構（I/P/B 影格），呈現順序（PTS）與解碼順序（DTS）不相同。
   - OpenCV 的 `CAP_PROP_POS_FRAMES` 尋找時，只會跳到前一個關鍵影格（Keyframe），之後計算 frame count 時經常出現 **10～30 格（約 0.5～1 秒）的累積偏移**。
2. **「所見非所得」的認知落差**：
   - 使用者在 GUI 畫面上看到的「Frame 7199」，其實是 OpenCV 解碼偏移後的影像（可能對應真實影片中的第 7215 格）。
   - 但 FFmpeg 轉檔引擎使用的是標準的 `trim=end_frame=7199` 與嚴格 PTS 解碼。
   - 結果：使用者以為剛好切到廣告起點，但其實真正的廣告早在 `7193` 就開始了；結束點也因為同樣的偏移，提早在 `7818` 恢復正片，導致兩端各漏掉了幾格，在拼接處湊成了整整 1 秒的廣告殘影。

---

## 2. 修改目標

- **100% 影格精確（Frame-Accurate）**：
  讓邊界檢查視圖（4-Frame Boundary View）看到的縮圖，與 FFmpeg 轉檔引擎所認定的影格編號完全同步，徹底消除「猜影格」的困擾。
- **兼顧流暢度**：
  保留一般時間軸快速拖曳的反應速度，僅在需要精確確認邊界（四格卡片）時採用精確解碼與快取機制。

---

## 3. 架構設計與實作策略

### 核心解法：FFmpeg 精確單格解碼器
不再單純依賴 OpenCV 的隨機 `CAP_PROP_POS_FRAMES`，改為在 `FrameExtractor` 中提供「精確抽格（Exact Frame）」能力：

```
[使用者點選候選廣告]
        │
        ▼
[BoundaryView 要求刷新 4 格邊界]
        │
        ▼
[FrameExtractor.get_exact_frame(f_idx)]
        │
        ├── 檢查記憶體 LRU 快取（命中則直接回傳）
        │
        └── 未命中：呼叫 FFmpeg 進行精確解碼（輸出 Raw BGR 或單張圖片）
                - 語法：ffmpeg -ss {pts} -i input.mp4 -vframes 1 -f image2pipe ...
                - 或使用 select 濾鏡精確抽取指定影格
```

---

## 4. 具體修改檔案與步驟

### 步驟 0：先診斷（約 10 分鐘，決定後續方向）
執行 [scripts/diagnose_frame_offset.py](../scripts/diagnose_frame_offset.py)：
```bash
uv run python scripts/diagnose_frame_offset.py <影片.mp4> 7193 7199 7818 7819
```
- 檢查 `start_time`、是否 VFR、各格 `pts_time`。
- OpenCV 與 FFmpeg 各抽一張並算 MAE（輸出到 `scripts/_diag/`）。
- **MAE 大** → 原因 A（OpenCV seek 偏移），照步驟一～二進行。
- **MAE 小但仍殘留** → 原因 B，重點改步驟三（exporter）。

---

### 步驟一：修改 `src/video_ad_remover/core/frame_extractor.py`
**目標**：新增基於 FFmpeg 的精確單格擷取方法，並加入簡易快取。

1. **新增 `get_exact_frame` 方法**：
   - 優先讀取對應影格的精確 PTS 時間戳：`pts = self.meta.time_of(frame_index)`。
   - **統一採用兩段式 seek**：先以 `-ss` 在 `-i` 前粗跳到目標前 N 秒（例如 3 秒），再用 `select` 精確取格，計數方式須與 exporter 完全一致：
     ```bash
     ffmpeg -ss {max(pts-3,0)} -i {video_path} -vf "select=eq(n\,K)" -vsync 0 -frames:v 1 -f image2pipe -c:v png pipe:1
     ```
     （K 為粗跳後的相對格數；實作時需以 ffprobe pts 校正，並用診斷腳本的「從頭解碼」結果作為基準比對。）
   - 將輸出的二進位 stream 透過 `cv2.imdecode` 解碼為 OpenCV `np.ndarray`（BGR 格式）。
2. **加入小型 LRU 快取機制**：
   - 使用 `collections.OrderedDict` 或 `functools.lru_cache` 快取最近抽取的 32 ~ 64 張精確影格。
   - 當使用者在邊界按 `[+1格]` 或 `[-1格]` 微調時，連續幾張影格可快速命中快取，確保介面完全不卡頓。
3. **批次抽格與非同步載入**：
   - 邊界 4 格改成**單次 ffmpeg 呼叫**輸出多張，不要開 4 個 process。
   - 在背景 thread（`QThreadPool`）載入，UI 先顯示 loading 佔位，避免卡住 GUI。
   - 預先抓邊界前後各 ±N 格，讓 `[+1格]` / `[-1格]` 微調直接命中快取。
   - LRU key 使用 `(video_path, frame_idx, target_size)`，切換影片時清空。

---

### 步驟二：修改 `src/video_ad_remover/gui/widgets/boundary_view.py`
**目標**：切換為精確抽格資料來源。

1. **修改 `BoundaryView.refresh()`**：
   - 將原本的：
     ```python
     img = self.extractor.get_frame(f_idx, target_size=(180, 100))
     ```
   - 改為呼叫精確抽格介面：
     ```python
     img = self.extractor.get_exact_frame(f_idx, target_size=(180, 100))
     ```
2. **改善微調手感**：
   - 確保在微調起點或終點時，4 張卡片（正片最後一格、廣告第一格、廣告最後一格、正片第一格）顯示的畫面 100% 反映真實影片交界。

---

### 步驟三：優化 `src/video_ad_remover/core/exporter.py`
**目標**：確保切片濾鏡（Filtergraph）與時間戳完全對齊。

1. **確認 CFR / VFR 裁切方式一致性**：
   - 在產生 `trim` 濾鏡時，確保使用的 `start_frame` / `end_frame` 或 `start` / `end` PTS 與 `VideoMetadata` 的計算邏輯嚴格對齊。
   - 如果使用 PTS 秒數裁切，統一使用 `time_of(seg.start_frame)` 與 `time_of(seg.end_frame)`。
   - 若 `start_time ≠ 0`，換算 PTS 時必須加上偏移。
2. **三者共用同一個 `VideoMetadata`**：`time_of()`、exporter 的 `trim`、`get_exact_frame` 必須使用同一套換算。新增單元測試：給定 frame N，三者算出的 PTS 必須一致。
3. **音訊同步**：`atrim` 的邊界必須使用與影像 `trim` 完全相同的 PTS 秒數（含 `asetpts=PTS-STARTPTS`），避免影像乾淨但聲音殘留廣告尾巴。
4. **匯出後自動驗證**：
   - 轉檔完成後，抽取接合點前後各 24 格，與原片「廣告起點前一格」「廣告終點後一格」做相似度比對（SSIM 或 perceptual hash）。
   - 若接合點附近仍比對到廣告特徵或對不上，於 UI 提示使用者。

---

## 5. 驗證與驗收標準

1. **邊界縮圖比對測試**：
   - 針對有 B-frame 的測試影片，選定廣告交界處。
   - 將 `BoundaryView` 擷取出的影格，與 FFmpeg 指令直接輸出的圖片進行比對（像素級相同或誤差小於解碼器色度差異）。
2. **完整轉檔驗證（重測 7199-7818 案例）**：
   - 使用者在修正後的 GUI 介面上重新檢查該廣告片段：
     - 若 OpenCV 之前有偏移，在修正後，介面縮圖會如實顯示「真正的廣告在 7193 就出現了」。
     - 使用者只要依照眼睛看到的畫面微調到廣告真正消失的第一格。
   - 轉檔完成後，播放新影片交界處，確認 `7193 - 7216` 區間完全乾淨、無任何廣告閃爍或音訊雜音。

---

## 6. 風險與回退

- 精確抽格較慢，因此**保留 OpenCV 快速模式**用於一般時間軸拖曳，僅在四格邊界檢視使用精確模式。
- 若 ffmpeg 不存在或逾時，自動退回 OpenCV，並在 UI 標示「非精確」。
- 若步驟 0 顯示問題在 exporter，則本計畫的步驟一、二降為選配，主力改步驟三。

---

## 7. 後續建議（選配增強）

- **邊界銜接快速試看（Preview Transition）**：
  在四格檢查下方提供「▶ 試看接合（前後 2 秒）」按鈕，直接以精確抽出的影格播放 4 秒快照動畫或暫存小短片，讓使用者在按下轉檔前就能 100% 放心。
